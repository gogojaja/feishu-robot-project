## 2. 架构策略

### 2.1 业务上下文

feishu-robot-project 是 OpenCode 编程助手提供飞书/Lark 移动端/桌面端接入能力的服务。用户可通过飞书消息界面进行编程开发，交互方式与终端使用 OpenCode 完全一致。

### 2.2 驱动因素

| 驱动因素 | 说明 |
|----------|------|
| **轻量级** | 适合单文件服务，无额外组件 |
| **易用性** | 学习成本低，开发效率高 |
| **稳定性** | Token 缓存、消息去重、限流保护 |
| **安全性** | 输入校验、限流、错误处理 |
| **可维护性** | 代码清晰、日志完善、会话持久化 |
| **可扩展性** | 水平扩展支持、配置外部化 |

### 2.3 质量属性

| 质量属性 | 权重 | 目标值 | 优先级 |
|----------|------|--------|--------|
| **可用性** | 30% | 99.9% | P0 |
| **安全性** | 25% | 无高危漏洞 | P0 |
| **性能** | 20% | P99 ≤ 200ms | P1 |
| **可维护性** | 15% | 代码可读/可测试 | P1 |
| **可扩展性** | 10% | 水平扩展 | P2 |

### 2.4 技术选型

| 技术组件 | 选型 | 版本 |
|----------|------|------|
| **后端框架** | Flask | 2.3.3+ |
| **Python 版本** | Python 3.11 | 3.11.x |
| **HTTP 客户端** | requests | 2.31.0+ |
| **配置管理** | pyyaml | 6.0+ |
| **容器化** | Docker | 20.10+ |

## 3. 4+1 视图

### 3.1 逻辑视图

- **领域模型**：FeishuBot 类、消息处理、OpenCode 调用
- **功能分解**：消息处理、限流检查、OpenCode 调用、会话管理、消息发送、Token 获取
- **类图**：FeishuBot 类包含多个方法

### 3.2 进程视图

- **并发模型**：主线程（Flask 事件循环）、工作线程（消息处理）、预热线程、子进程（OpenCode 调用）
- **同步机制**：线程锁保护（_dedup_lock、_rate_lock、_session_lock）

### 3.3 开发视图

- **模块分层**：表现层（webhook、api_chat、chat_page、health）、业务层（_process、_run、_check_rate_limit）、数据层（_load_sessions、_save_sessions、_processed_ids）、基础设施层（get_token、send、_strip、_truncate）
- **依赖关系**：API 路由组件 → 消息处理组件 → OpenCode 调用组件 → 消息发送组件 → Token 获取组件

### 3.4 物理视图

- **部署拓扑**：飞书客户端 → 飞书开放平台 → Flask 服务（Port 5103） → OpenCode Server（Port 5102）
- **网络拓扑**：Flask 服务（Port 5103）、OpenCode Server（Port 5102）

### 3.5 场景视图

- **场景 1**：用户发送消息 → 飞书开放平台 → Flask 服务 → OpenCode Server → 用户
- **场景 2**：消息限流触发 → 固定窗口限流 → 拒绝第 11 条消息
- **场景 3**：Token 获取失败 → Token 失败告警 → 服务降级
- **场景 4**：会话持久化 → 会话落盘 → 会话恢复

## 6. 接口设计

### 6.1 REST API 接口

| 接口路径 | 请求方法 | 认证 | 限流 | 说明 |
|----------|----------|------|------|------|
| `/feishu/events` | POST | 飞书签名 | 10 条/分钟 | 飞书事件 Webhook |
| `/webhook_sys` | POST | 无 | 10 条/分钟 | 系统事件 Webhook |
| `/webhook_chat` | POST | 无 | 10 条/分钟 | 群聊事件 Webhook |
| `/api/chat` | POST | 无 | 10 条/分钟 | REST API 聊天 |
| `/chat` | GET | 无 | 无 | Web 聊天页面 |
| `/health` | GET | 无 | 无 | 健康检查 |

### 6.2 API 版本管理

- **版本策略**：不使用 URL 版本、不使用 Header 版本、使用 PATCH 版本
- **版本兼容性**：v1.0（初始版本）

### 6.3 错误码规范

| 错误码 | 说明 | HTTP 状态码 |
|--------|------|-------------|
| `200` | 成功 | 200 |
| `400` | 请求参数错误 | 400 |
| `401` | 认证失败 | 401 |
| `403` | 权限不足 | 403 |
| `500` | 服务器内部错误 | 500 |
| `503` | 服务不可用 | 503 |

## 7. 部署设计

### 7.1 部署拓扑

- **物理部署拓扑**：飞书客户端 → 飞书开放平台 → 负载均衡器（可选） → Flask 服务 → OpenCode Server

### 7.3 容器化

- **Docker 容器**：Dockerfile、docker-compose.yml

## 8. 数据架构设计

### 8.1 ER 模型

- **实体识别**：User、Session、Message
- **ER 图**：User → Session → Message

### 8.2 数据字典

详见《数据字典》文档

### 8.3 存储策略

- **会话数据**：文件系统（var/sessions.json）
- **消息数据**：内存（_processed_ids）
- **限流记录**：内存（_rate_limits）
- **Token 状态**：内存（tenant_access_token + token_expire_time）

### 8.4 数据流转

- **数据流向**：用户 → 飞书开放平台 → Flask 服务 → 文件系统
- **ETL/同步**：会话数据文件同步、消息数据内存同步

### 8.5 数据生命周期

- **数据保留**：会话数据 7 天、消息数据不保留、限流记录不保留、Token 状态不保留
- **数据销毁**：会话数据 7 天后自动删除
- **数据分级**：公开数据（消息内容）、内部数据（会话数据）、敏感数据（Token）

- **网络层**：无（内网部署）
- **应用层**：输入校验、安全编码、防绕过
- **数据层**：Token 存储在内存中、权限管控、审计
- **最小权限**：服务账号最小权限、安全边界、凭证管理

## 13. 七原则合规检查

### 13.1 成熟性

- **技术栈 LTS 版本**：Python 3.11、Flask 2.3.3+、requests 2.31.0+、pyyaml 6.0+
- **生产案例**：Flask、Python、requests 均有大量生产案例

### 13.2 稳定性

- **冗余设计**：Token 缓存、消息去重、限流保护
- **故障隔离**：异常捕获、超时控制、熔断降级
- **高可用设计**：Token 连续失败告警、服务降级

### 13.3 安全性

- **STRIDE 全覆盖**：六类威胁全覆盖
- **认证授权**：Token 验证、限流保护
- **数据安全**：输入校验、限流保护、错误处理
- **审计链**：日志记录、消息去重

### 13.4 高效性

- **性能预算**：P99 ≤ 200ms
- **异步处理**：异步消息处理、异步预热
- **缓存策略**：Token 缓存

### 13.5 便捷性

- **分层清晰**：表现层、业务层、数据层、基础设施层
- **模块职责单一**：每个方法/函数只负责一个功能
- **代码可读性**：变量/函数命名清晰、注释完善

### 13.6 跨平台性

- **平台差异抽象**：使用 `pathlib` 抽象平台差异
- **厂商锁定避免**：使用标准库，不依赖厂商专有 API
- **标准协议**：HTTP/HTTPS 标准

### 13.7 可移植性

- **配置外部化**：配置文件 + 环境变量
- **无状态化**：会话落盘、标准化接口
- **12-Factor**：配置外部化、日志输出、进程模型、依赖外部化、无状态进程

## 1. 业务上下文分析

**产品定位**：通过飞书/Lark 移动端或桌面端调用本机 OpenCode 进行编程开发，交互方式与终端使用 OpenCode 完全一致。

**用户特征**（SRS 02）：
- 单用户 + AI 助理模式（项目负责人段波），消息来源为飞书用户 open_id
- 用户规模极小（1 用户），并发量低，但要求响应可靠

**核心价值流**：
```
飞书用户 ──(im.message.receive_v1)──> 机器人服务 ──(subprocess)──> OpenCode CLI ──> 模型
飞书用户 <──(im/v1/messages 发送)──── 机器人服务 <──(JSON stream)── OpenCode CLI
```

**关键假设**：无外部采购预算；测试环境端口可用；opencode CLI 已安装（v1.17.4）。

## 4. 架构权衡分析（ATAM 简化）

### 4.1 关键权衡点 T1：事件接入方式
- **候选 A（存量）**：Webhook 模式，Flask 接收 POST → 需公网回拨（内网 5103 需 ngrok 穿透）
- **候选 B**：飞书官方长连接 SDK（WebSocket），无需公网 IP，官方推荐
- **权衡**：存量代码已稳定运行且 Webhook 为社区大量验证的成熟模式；长连接免穿透但引入 SDK 依赖与 3 秒处理限制。**决策**：Webhook 为主，长连接留作迁移预案。

### 4.2 关键权衡点 T2：OpenCode 会话连续
- **候选 A（存量）**：`opencode run --session <sid>` 子进程复用，官方 CLI 支持
- **候选 B**：`opencode serve` + `run --attach` 常驻 server
- **权衡**：存量 A 简单、无常驻进程占用，官方文档明确支持 `--session`；B 并发更强但引入常驻 server 与端口占用。单用户低并发场景 **决策：A 为主**。

### 4.3 关键权衡点 T3：会话与状态存储
- **候选 A（存量）**：内存 dict + threading.Lock
- **候选 B**：Redis 持久化
- **权衡**：SRS REQ-DATA-REQ-001 明确「消息不落盘仅内存态」→ **决策：A**，符合隐私需求且零成本。

### 4.4 权衡总结
安全性 > 长期稳定性 > 技术成熟度 > 部署便捷度 > 日常使用便捷度（AGENTS.md §19）。
本项目全部选型遵循「复用存量稳定实现 + 零采购」，在单用户低并发假设下成立。

## 5. 技术选型结论

| 决策项 | 结论 | 依据 |
|--------|------|------|
| 事件接入 | Webhook（Flask）+ ngrok 内网穿透；长连接 SDK 为迁移预案 | 官方文档 + 社区项目验证 |
| Web 框架 | Flask（threaded=True） | 存量代码 + SRS 06 |
| HTTP 客户端 | requests | 存量代码 |
| OpenCode 调用 | subprocess.run + `--session`（180s 超时） | 官方 CLI 文档验证 |
| 会话存储 | 内存 dict + threading.Lock | REQ-FUNC-REQ-013 / REQ-DATA-REQ-001 |
| 去重 | 内存 set + Lock（message_id 幂等） | REQ-FUNC-REQ-003 |
| 限流 | 内存固定窗口（10 条/分钟/open_id） | REQ-SEC-REQ-003 |
| 配置 | 环境变量优先 → config/feishu.yaml | REQ-ENV-REQ-002 |
